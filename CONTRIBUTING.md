# Contributing

Thanks for helping improve the course! Notebooks are the source of truth.

## Setup
```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt nbconvert
```

## Rules for notebooks
* **Keep outputs cleared** in committed notebooks (`jupyter nbconvert --clear-output --inplace <file>`). CI rejects stored outputs.
* **Every lesson must run top to bottom** with `MPLBACKEND=Agg`:
  ```bash
  MPLBACKEND=Agg jupyter nbconvert --to notebook --execute --output-dir /tmp/out modules/NN-name/lesson.ipynb
  ```
* **A cell that prints a failure but doesn't raise is a hidden bug** (e.g. `doctest` or a subprocess). Assert on the result so CI notices.
* **Claims in prose must match the output.** If you write "the CI is about (−0.3, 6.1)", check the printed number.
* Keep data loading via the shared `DATA` setup cell so notebooks work locally and in Colab.

## Exercises
* Each exercise = prompt, a starter that **does not pass its own check**, a solution, and a **check cell** that raises `AssertionError` with a helpful hint.
* Solutions live in `solutions/NN-name/exercises_solutions.ipynb` and must pass all checks.
* Checks should accept any correct approach (use tolerances for randomness; inspect behaviour, not exact code).
* Confirm both directions: solutions pass **and** the unsolved notebook passes none of its checks.

## Package exercises (Modules 6.5 and 11)
* `modules/.../exercise/` (student stub) and `solutions/.../exercise/` (reference) share the same tests/checker.
* The reference must pass; the stub must still fail. CI enforces both.

## Datasets
* Bundled data are **synthetic** and generated by `data/generate_datasets.py` with fixed seeds. If you change a dataset, re-run the generator, update `data/README.md`, and re-check every exercise that depends on exact values (CI will tell you which).
* Never commit real personal data.

## Projects
* `projects/template/` and `projects/worked-example/` are tested in CI (`pytest`, `run_analysis.py`, notebooks, project doctor).
* The worked example has a test that fails if its README's headline numbers go stale; update the README when results change.

## Style
* Python: clear names, docstrings for public functions, standard library and the course's dependencies only.
* Markdown: short sentences, concrete examples, math in `$...$`. Prefer showing a result before explaining it.
* Don't make claims you haven't verified (about the data, about library behaviour, about the maths).

## Before opening a pull request
1. Run the changed notebooks (and anything that depends on them) top to bottom.
2. Run `pytest` in any package you touched.
3. Run `python projects/check_project.py projects/worked-example` if you touched the projects.
4. Write a clear description: what changed, why, and how you verified it.
